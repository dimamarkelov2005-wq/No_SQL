## 1. Цель работы и описание предметной области

**Цель работы:** Спроектировать стратегию горизонтального масштабирования документоориентированного хранилища, выбрать оптимальный `shard key` на основе шаблонов доступа (Access Patterns), количественно проверить распределение документов и нагрузки, выявить «горячие» шарды (hot shards) и аргументировать архитектурное решение.

**Предметная область (Вариант №1 — Интернет-магазин):**
Система обрабатывает поток заказов пользователей. В рамках симуляции смоделирован кластер из **3 шардов** (`Shard A`, `Shard B`, `Shard C`), содержащий **$N = 12\,000$ документов** (заказов) и обрабатывающий **$Q = 30\,000$ запросов**.

## 2. Архитектура маршрутизации запросов

В шардированном кластере MongoDB приложение взаимодействует не напрямую с узлами хранения, а через маршрутизатор запросов **`mongos`**, который определяет целевой шард на основе значения `shard key`.

```text
+--------------------+         +-------------------------+         +-----------------------+
|     Приложение     |         |         mongos          |-------->| Shard A (Часть данных)|
| (Чтение и запись   |-------->| (Маршрутизация запросов |         +-----------------------+
| по Access Pattern) |         |      по shard key)      |-------->| Shard B (Часть данных)|
+--------------------+         +-------------------------+         +-----------------------+
                                                           -------->| Shard C (Часть данных)|
                                                                   +-----------------------+
```

## 3. Анализ шаблонов доступа (Access Patterns)

| ID | Описание шаблона доступа (Access Pattern) | Фильтр запроса | Тип маршрутизации (при `hashed customer_id`) |
| :--- | :--- | :--- | :--- |
| **AP-01** | Получение истории покупок конкретного клиента *(основной запрос)* | `{ customer_id: X }` | **Targeted** (обращение к 1 шарду) |
| **AP-02** | Выборка заказов за определенный интервал времени / ID | `{ order_id: { $gte: A, $lte: B } }` | **Scatter-gather** (опрос всех шардов) |
| **AP-03** | Агрегация статистики продаж по категории товаров | `{ category: Y }` | **Scatter-gather** (опрос всех шардов) |
| **AP-04** | Загрузка нового потока входящих заказов (вставка) | `insertOne({ customer_id, ... })` | **Targeted** (равномерно по всем шардам) |
| **AP-05** | Поиск конкретного заказа клиента по его ID и категории | `{ customer_id: X, category: Y }` | **Targeted** (по префиксу `customer_id`) |
| **AP-06** | Получение общего количества заказов в системе за сутки | `countDocuments({ date: Z })` | **Scatter-gather** (опрос всех шардов) |

## 4. Оценка кандидатов Shard Key

1. **`category` (низкокардинальный ключ):**
   * *Кардинальность:* Очень низкая (всего 5 уникальных значений: `0..4`).
   * *Монотонность:* Отсутствует.
   * *Проблема:* При 3 шардах распределение по остатку от деления (`category % 3`) сразу создает перекос объемов данных (`4800 / 4800 / 2400`), а всплеск популярности одной категории вызывает критическую перегрузку одного шарда.
2. **`customer_id` с хэшированием (`hashed`):**
   * *Кардинальность:* Высокая ($2\,500$ уникальных клиентов).
   * *Монотонность:* Устраняется за счет криптографического хэширования (SHA-256 в симуляции / MD5 в MongoDB).
   * *Преимущество:* Обеспечивает равномерное распределение как документов, так и запросов даже при сильном перекосе популярности отдельных категорий товаров.
3. **`order_id` (диапазонный / `ranged`):**
   * *Кардинальность:* Максимальная ($12\,000$ уникальных значений).
   * *Монотонность:* Строго монотонный рост ($0, 1, 2, \dots, N-1$).
   * *Проблема:* Идеально делит исторические данные поровну, но в реальной системе все новые записи (`AP-04`) будут попадать исключительно в последний диапазон (на один «горячий» шард).

## 5. Результаты экспериментальной симуляции

Симуляция выполнена на языке Python 3 с фиксированным генератором случайных чисел (`random.seed(42)`). Проверены два режима нагрузки:
* **`uniform`** — равномерное распределение запросов по всем заказам.
* **`hot`** — $60\%$ всех запросов направлены на заказы одной популярной категории (`category == 0`).

### Таблица результатов распределения

| Кандидат / Режим нагрузки | Документы (Shard A / B / C) | Запросы (Shard A / B / C) | Коэф. `doc max/mean` | Коэф. `query max/mean` |
| :--- | :---: | :---: | :---: | :---: |
| **`category` / uniform** | `4800 / 4800 / 2400` | `11947 / 12018 / 6035` | `1.20` | `1.20` |
| **`category` / hot** | `4800 / 4800 / 2400` | `22828 / 4822 / 2350` | `1.20` | **`2.28` (Hot Shard!)** |
| **`hashed_customer` / uniform** | `3866 / 3805 / 4329` | `9608 / 9435 / 10957` | `1.08` | `1.10` |
| **`hashed_customer` / hot** | `3866 / 3805 / 4329` | `9261 / 9774 / 10965` | `1.08` | **`1.10` (Стабильно)** |
| **`range_order` / uniform** | `4000 / 4000 / 4000` | `10046 / 9958 / 9996` | `1.00` | `1.00` |
| **`range_order` / hot** | `4000 / 4000 / 4000` | `9967 / 9985 / 10048` | `1.00` | `1.00` |

## 6. Улучшение модели и составной ключ (Compound Shard Key)

При дальнейшем росте системы и появлении «супер-покупателей» (например, оптовых клиентов с миллионами заказов) даже ключ `hashed_customer` может привести к образованию неделимых чанков (jumbo chunks).

**Рекомендуемое улучшение:** Использование составного ключа `{ customer_id: "hashed", order_id: 1 }` (или `{ customer_id: 1, day_bucket: 1 }`).
* **Аргумент 1 (Кардинальность):** Комбинация клиента и временного бакета/заказа обеспечивает практически бесконечную кардинальность.
* **Аргумент 2 (Локализация диапазонов):** Позволяет эффективно выполнять запросы истории конкретного клиента за определенный период без полного сканирования всех его заказов.
* **Аргумент 3 (Защита от Jumbo Chunks):** Балансировщик MongoDB сможет дробить данные даже одного очень активного клиента на несколько чанков.
* **Ограничение:** Для `targeted`-маршрутизации приложение обязано всегда передавать `customer_id` в условии фильтра `find()`.

## 7. Краткие ответы на контрольные вопросы

1. **Чем шардирование отличается от репликации?**  
   Репликация создает полные копии одних и тех же данных на разных узлах для отказоустойчивости и чтения. Шардирование делит большой набор данных на части (чанки) между независимыми серверами для горизонтального масштабирования объема и пропускной способности записи.
2. **Почему равномерное размещение документов не гарантирует равномерной нагрузки?**  
   Даже если на каждом шарде хранится одинаковое число документов, пользовательские запросы могут обращаться преимущественно к определенному подмножеству данных (например, к товарам одной популярной категории или свежим записям), создавая «горячий шард» по CPU и I/O.
3. **Как интерпретировать коэффициент `max/mean`?**  
   Значение `1.0` означает идеальное равномерное распределение. Чем сильнее значение превышает `1.0` (например, `2.28` у `category/hot`), тем сильнее перегружен самый загруженный шард относительно среднего показателя по кластеру.
4. **Какие ограничения имеет Python-симуляция по сравнению с реальным MongoDB?**  
   Симуляция использует упрощенное деление по модулю (`% SHARDS`), не учитывает работу фонового балансировщика (Balancer), физическое дробление данных на чанки (Chunks по 64/128 МБ) и накладные расходы на сетевую агрегацию в `mongos`.

## 9. Заключение

В ходе лабораторной работы проведено сравнительное исследование трех стратегий шардирования для системы интернет-магазина. Экспериментально доказано, что низкокардинальный ключ `category` непригоден для масштабирования, так как при перекосе популярности товаров нагрузка на `Shard A` возрастает более чем в два раза (`query_max_mean = 2.28`). Оптимальным решением для данного класса задач является стратегия **`hashed_customer`** (хэширование `customer_id`), которая обеспечивает равномерное распределение нагрузки (`query_max_mean = 1.10`) и позволяет выполнять основной паттерн доступа (`AP-01` — покупки клиента) в режиме `targeted query`.
