### 3. Схема Replica Set

```
┌─────────────────────┐     ┌─────────────────────┐     ┌─────────────────────┐
│  127.0.0.1:27101    │     │  127.0.0.1:27102    │     │  127.0.0.1:27103    │
│  (PRIMARY / SECONDARY)│◄──►│  (PRIMARY / SECONDARY)│◄──►│  (PRIMARY / SECONDARY)│
│  dbpath: .../rs1    │     │  dbpath: .../rs2    │     │  dbpath: .../rs3    │
└─────────────────────┘     └─────────────────────┘     └─────────────────────┘
         ▲                           ▲                           ▲
         └───────────────────────────┴───────────────────────────┘
                          Replica Set: rsLab10
```

**Роли до отказа (пример):**
- 127.0.0.1:27101 — PRIMARY  
- 127.0.0.1:27102 — SECONDARY  
- 127.0.0.1:27103 — SECONDARY

### 4. Используемые команды

#### Запуск экземпляров
```bash
mongod --replSet rsLab10 --port 27101 --dbpath ~/mongo-lab10/rs1 --bind_ip 127.0.0.1
mongod --replSet rsLab10 --port 27102 --dbpath ~/mongo-lab10/rs2 --bind_ip 127.0.0.1
mongod --replSet rsLab10 --port 27103 --dbpath ~/mongo-lab10/rs3 --bind_ip 127.0.0.1
```

#### Инициализация
```javascript
rs.initiate({
  _id: "rsLab10",
  members: [
    { _id: 0, host: "127.0.0.1:27101" },
    { _id: 1, host: "127.0.0.1:27102" },
    { _id: 2, host: "127.0.0.1:27103" }
  ]
})
```

#### Запись тестовых данных (writeConcern majority)
```javascript
use university_lab10
db.orders.insertMany([ /* 22 документа */ ], { writeConcern: { w: "majority", wtimeout: 5000 } })
```

#### Резервное копирование
```bash
mongodump --uri="mongodb://127.0.0.1:27101/?replicaSet=rsLab10" --db=university_lab10 --out=./backup_lab10
mongorestore --uri="mongodb://127.0.0.1:27101/?replicaSet=rsLab10" \
             --nsFrom="university_lab10.*" --nsTo="university_restore10.*" \
             ./backup_lab10/university_lab10
```

### 7. Анализ RPO и RTO

**Наблюдаемое время переключения (RTO):**  
t1 − t0 ≈ 5–15 секунд (на учебном стенде).

**Оценка RPO:**  
Запись выполнялась с `w: "majority"`. После failover все 22 документа сохранились.  
Фактическая потеря данных = 0 (в условиях эксперимента).  
Это **не доказывает** RPO = 0 в промышленной среде.

**Целевые показатели для варианта (проектные допущения):**
- **RPO** ≤ 1 минута (допустима потеря последних незафиксированных заказов)
- **RTO** ≤ 30 секунд (быстрое переключение для интернет-магазина)

**Критичность потери данных:**  
Высокая. Потеря заказов приводит к финансовым потерям, претензиям клиентов и нарушению учёта. Поэтому требуется:
- writeConcern majority;
- регулярные бэкапы;
- мониторинг replication lag.

---

### 9. Выводы

1. **Репликация** обеспечивает высокую доступность (автоматический failover при потере PRIMARY) и защиту от отказа одного узла.  
2. **Резервное копирование** защищает от логических ошибок (случайное удаление, порча данных), которые тоже реплицируются.  
3. `w: "majority"` гарантирует, что запись подтверждена большинством узлов, но **не заменяет** backup.  
4. Учебный стенд имеет ограничения:
   - малая нагрузка;
   - отсутствие сетевых задержек и реальных сбоев;
   - нет аутентификации и TLS;
   - измеренное RTO/RPO не переносится напрямую на промышленную среду.

**Репликация + backup** — необходимый минимум для систем, где потеря данных недопустима (интернет-магазин).

### 10. Ответы на контрольные вопросы (кратко)

| №  | Вопрос                                      | Ответ |
|----|---------------------------------------------|-------|
| 7  | Чем репликация отличается от backup?        | Репликация — копии в реальном времени для доступности. Backup — снимок на момент времени для восстановления после ошибок. |
| 8  | Почему нужен кворум?                        | Чтобы избежать split-brain и гарантировать, что выбранный PRIMARY видит большинство узлов. |
| 9  | Роль primary                                | Принимает все операции записи, ведёт oplog. |
| 10 | Потеря большинства                          | Выборы невозможны, набор становится недоступным для записи. |
| 11 | Почему w:majority ≠ backup                  | majority не защищает от ошибочного удаления/изменения данных. |
| 12 | Как измерить failover                       | Зафиксировать t0 (остановка) и t1 (появление нового PRIMARY). |
| 13 | RPO и RTO                                   | RPO — допустимая потеря данных во времени. RTO — допустимое время восстановления. |
| 14 | Почему restore в отдельную базу             | Чтобы не затереть рабочие данные и безопасно проверить целостность. |
| 15 | Риски остановки primary                     | Временная недоступность записи, возможный lag, кратковременные ошибки клиентов. |
| 16 | Ограничения учебного стенда                 | Нет реальной нагрузки, сети, безопасности, мониторинга. |
